# Contributing to HappyView

Thanks for helping out! This guide covers what a pull request needs to get merged.

## Open pull requests against `dev`

All work lands on `dev` first, and `main` is updated from `dev` when a release is cut.

GitHub defaults new PRs to `main`, so change the **base** dropdown to `dev` when you open one. To start from the right place:

```bash
git remote add upstream https://github.com/gamesgamesgamesgamesgames/happyview.git
git fetch upstream
git switch -c fix/my-change upstream/dev
```

If your branch was started from `main`, rebase it onto `dev`:

```bash
git rebase --onto upstream/dev upstream/main fix/my-change
```

## Sign off your commits

Every commit needs a `Signed-off-by` line certifying the [Developer Certificate of Origin](https://developercertificate.org/). The DCO check is required, so a PR can't be merged without it.

Add it with `-s`:

```bash
git commit -s -m "fix: handle empty lexicon lists"
```

Git has no setting to sign off automatically, but an alias saves typing: `git config alias.cs "commit -s"`.

### If the DCO check fails

Either sign off the existing commits and force-push:

```bash
git rebase --signoff upstream/dev
git push --force-with-lease
```

or, if you'd rather not rewrite history, push one more signed-off commit. Its sign-off covers the earlier commits in the PR:

```bash
git commit --allow-empty -s -m "chore: sign off previous commits"
git push
```

## Commit messages

Releases are generated by semantic-release, so commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `fix:`, `feat:`, `docs:`, `test:`, `ci:`, `chore:`, and so on. Use `feat!:` or a `BREAKING CHANGE:` footer for breaking changes.

## Local setup

Point git at the tracked hooks once per clone:

```bash
git config core.hooksPath .githooks
```

- **pre-commit** runs `cargo fmt --check` and `cargo clippy` over the lib and bins.
- **pre-push** runs `cargo clippy --all-targets`, which also covers test code.

## What CI checks

These checks must pass before merging:

| Check                   | Run it locally                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lint`                  | `cargo fmt -- --check` and `cargo clippy --workspace --all-targets -- -D warnings`                                                                        |
| `unit-tests`            | `cargo test --lib` and `cargo test --workspace --exclude happyview`                                                                                       |
| `e2e-tests`             | `cargo test --tests` with `TEST_DATABASE_URL` pointing at a Postgres database (`docker compose -f docker-compose.test.yml up -d` starts one on port 5433) |
| `frontend`              | `npm ci && npm run build` in `web/`                                                                                                                       |
| `test-*` (SDK packages) | `bun install`, then `bun run --filter '<package>' build`, `typecheck`, and `test`                                                                         |
| `DCO`                   | See [Sign off your commits](#sign-off-your-commits)                                                                                                       |

Jobs only run when the files they cover change, so a docs-only PR skips the Rust and frontend checks.

- **First-time contributors** need a maintainer to approve CI before it runs on your PR. Nothing is wrong if checks show as waiting.
- **`audit`** fails when a new RustSec advisory affects a dependency. That usually comes from the base branch rather than your change; a maintainer will handle it.
- **PR builds**: when your PR touches the server, CI builds Docker images and binaries, and a bot comments with `docker pull ghcr.io/gamesgamesgamesgamesgames/happyview:pr-<number>` so reviewers can try it.
